— Security

  
Ownership & Access Guards


  

    
🛡️ Recruiter cannot edit another recruiter's job

    
Before any PUT /api/jobs/:id or DELETE /api/jobs/:id, the controller fetches the job and compares job.recruiter_id === req.user.id. A mismatch returns 403 Forbidden immediately — Prisma never executes the update.

  


  

    
🛡️ Recruiter cannot view applicants of another recruiter's job

    
GET /api/jobs/:id/applications first queries the job by ID. If job.recruiter_id !== req.user.id, the endpoint returns 403 before any application rows are fetched. The check lives above the applicant query so there is no data leak even on error paths.

  


  

    
🛡️ One application per candidate per job (unique constraint)

    
The applications table has a Prisma @@unique([candidate_id, job_id]) constraint. The controller also checks for a duplicate before inserting and returns a clear 409 Conflict message: "You have already applied to this job."

  


  

    
🛡️ Candidates cannot apply to closed jobs

    
POST /api/jobs/:id/apply fetches the job first. If job.status === 'closed', it returns 400 Bad Request with "This job is no longer accepting applications." before any database write.

  


  
  

    
JSserver/controllers/jobs.js — ownership check pattern

    
// Security: verify the requesting recruiter owns this job
// before allowing any mutation or applicant read.
const job = await prisma.job.findUnique({ where: { id } });
if (!job) return res.status(404).json({ success: false, message: "Job not found." });

// Security: block recruiters from touching jobs they don't own.
if (job.recruiter_id !== req.user.id)
  return res.status(403).json({ success: false, message: "Forbidden — you do not own this job." });

— Implementation

  
Key Code Snippets


  

    
JSserver/utils/skills.js — alias dictionary + word-boundary matcher

    
// 150+ skills with aliases. "js" / "javascript" → same canonical skill.
const SKILL_MAP = [
  { canonical: 'javascript', aliases: ['javascript', 'js'] },
  { canonical: 'typescript', aliases: ['typescript', 'ts'] },
  { canonical: 'nodejs',     aliases: ['nodejs', 'node.js', 'node'] },
  { canonical: 'python',     aliases: ['python', 'py'] },
  { canonical: 'react',      aliases: ['react', 'reactjs', 'react.js'] },
  // … 145+ more entries …
];

// Word-boundary regex so "java" won't fire inside "javascript".
function extractSkills(text) {
  const lower = text.toLowerCase();
  const found = new Set();
  for (const { canonical, aliases } of SKILL_MAP) {
    for (const alias of aliases) {
      const re = new RegExp(`\\b${escapeRegex(alias)}\\b`, 'i');
      if (re.test(lower)) { found.add(canonical); break; }
    }
  }
  return [...found];
}

  


  

    
JSserver/utils/matcher.js — match percentage calculation

    
// matchPercentage = matched ÷ total required × 100 (rounded).
// Returns 0 (not null) when job has no required skills to avoid division by zero.
function matchResume(candidateSkills, requiredSkills) {
  if (!requiredSkills.length) {
    return { match_percentage: 0, matched_skills: [], missing_skills: [] };
  }
  const cSet = new Set(candidateSkills.map(s => s.toLowerCase()));
  const matched = requiredSkills.filter(s => cSet.has(s.toLowerCase()));
  const missing = requiredSkills.filter(s => !cSet.has(s.toLowerCase()));
  return {
    match_percentage: Math.round((matched.length / requiredSkills.length) * 100),
    matched_skills: matched,
    missing_skills: missing,
  };
}

  


  

    
JSserver/routes/jobs.js — apply endpoint saves match at write-time

    
// POST /api/jobs/:id/apply

  where: { user_id: req.user.id }

  data: { job_id: id, candidate_id: req.user.id, cover_note,

Security Hardening

Helmet — HTTP security headers

        
helmet() sets X-Content-Type-Options, X-Frame-Options, Strict-Transport-Security, Content-Security-Policy, and 10 other headers in one call. Added as the first middleware in app.js.

      

      npm: helmet
    

    

      
🌐

      

        
CORS — origin whitelist from env

        
cors({ origin: process.env.CLIENT_ORIGIN }) — only the exact frontend URL is allowed. Wildcard * is never used. Unknown origins receive a CORS error before reaching any route handler.

      

      npm: cors
    

    

      
⏱️

      

        
Rate limiting — two tiers

        
Auth routes (/api/auth/login, /api/auth/register): 10 req / 15 min per IP — slows brute-force attempts. All other routes: 100 req / 15 min. Exceeded requests get 429 Too Many Requests with a Retry-After header.

      

      express-rate-limit
    

    

      
🧹

      

        
Input sanitisation — XSS prevention

        
express-mongo-sanitize strips $ and . operators. All string inputs are trimmed and length-capped before reaching Prisma. Prisma uses parameterised queries by default — raw SQL is never constructed from user input.

      

      Pattern
    

    

      
🔒

      

        
No password hashes or stack traces in responses

        
The central error handler in server/middleware/errorHandler.js strips the password_hash field from any object before serialising, and replaces raw stack traces with "Internal server error" in production (NODE_ENV=production).

      

      Pattern
    

    

      
📄

      

        
PDF magic-byte verification

        
Beyond checking the file extension, the upload middleware reads the first 4 bytes of every uploaded file and verifies they equal %PDF (25 50 44 46 in hex). A renamed .exe renamed to .pdf is rejected with 415 Unsupported Media Type before multer saves it.

      

      Magic bytes
    

  


  

    
JSserver/middleware/upload.js — magic-byte PDF check

    
const multer = require('multer');

// Verify first 4 bytes equal "%PDF" — rejects renamed executables.
function pdfFilter(req, file, cb) {
  if (file.mimetype !== 'application/pdf') {
    return cb(new Error('Only PDF files are allowed.'), false);
  }
  // Buffer the first chunk to read magic bytes before saving to disk.
  let header = Buffer.alloc(0);
  file.stream.once('data', (chunk) => {
    header = chunk.slice(0, 4);
    const isPDF = header.toString('hex') === '25504446'; // %PDF
    if (!isPDF) return cb(new Error('File content does not match PDF format.'), false);
    cb(null, true);
  });
}

const upload = multer({
  storage: multer.diskStorage({
    destination: 'server/uploads/',
    filename: (req, file, cb) => cb(null, `resume_${req.user.id}_${Date.now()}.pdf`)
  }),
  fileFilter: pdfFilter,
  limits: { fileSize: 3 * 1024 * 1024 } // 3 MB hard limit
});

— Database

  
Indexes & Why They Exist


  

    

      
TableIndex Column(s)Prisma DefinitionReason

      
        

          jobs
          status
          @@index([status])
          The browse endpoint filters WHERE status = 'open' on every page load. Without this index Postgres scans all job rows; with it, only open rows are touched.
        

        

          jobs
          location
          @@index([location])
          Location is a common filter param. An index lets Postgres skip the full table scan when candidates filter by city.
        

        

          jobs
          status, created_at
          @@index([status, created_at])
          Composite index for the default browse sort: open jobs ordered by newest first. Postgres uses both columns in a single index scan rather than a separate sort step.
        

        

          applications
          job_id
          @@index([job_id])
          Every recruiter applicants query filters WHERE job_id = ?. Without this, Postgres reads every row in applications to find the right ones.
        

        

          applications
          candidate_id
          @@index([candidate_id])
          The "my applications" endpoint filters WHERE candidate_id = ?. This index makes that O(log n) instead of O(n).
        

        

          applications
          job_id, match_percentage
          @@index([job_id, match_percentage])
          Recruiter views applicants sorted by match % DESC. The composite index allows Postgres to both filter by job and return rows pre-sorted, avoiding an in-memory sort.

— Scalability

  
What I'd Improve with 10,000 Users


  

    

      
⚡

      
Redis Caching

      
Cache the browse jobs list (invalidated on new job or status change) and recommended-jobs scores per candidate. Eliminates repeated full-table reads for the most common endpoints.

    

    

      
🗂️

      
DB Indexes

      
Already added indexes on jobs(status, created_at), applications(job_id, match_percentage). At scale, also add a GIN index on required_skills for skill-based full-text search.

    

    

      
☁️

      
S3 for Resume Files

      
Storing uploads on disk doesn't scale horizontally (each server instance has its own disk). Move to S3 or compatible object storage with pre-signed URLs for download — single source of truth across all instances.

    

    

      
📬

      
Queue Resume Processing

      
PDF parsing and skill extraction are CPU-bound. At volume, offload them to a BullMQ / Redis queue so the HTTP response returns immediately (202 Accepted) and a worker processes asynchronously.

    

    

      
🔍

      
Full-Text Search

      
Replace the SQL ILIKE search with PostgreSQL tsvector full-text indexes, or move to Elasticsearch for ranked, typo-tolerant job search across titles and descriptions.

    

    

      
🔄

      
Horizontal Scaling

      
Stateless JWT means any server instance can handle any request. Add a load balancer (nginx or AWS ALB) in front of multiple server replicas. Session stickiness is not needed.
